## Corpus self-test (1-30)

**1.** Local `%name` vs global `@name`; where target triples are declared
`%` is a function-scoped SSA name (local, defined once per function), while `@` is module-scope (a global, constant, or function symbol visible across functions and possibly across modules). Each `%name` has exactly one definition with one type, and `@` is always module-scope. Modules declare their target in `target triple = "<arch>-<vendor>-<sys>-<env>"` (e.g. `x86_64-pc-linux-gnu`) at module top level, alongside `target datalayout` and `source_filename`. Using `@` for a local or `%` for a module symbol is always wrong.
_src: `llvm-training/01-syntax/01-modules-functions-blocks.md`_

**2.** Why a `phi` incoming block list must match CFG predecessors exactly
A `phi` must list one `(value, predecessor-label)` pair for every basic block that actually branches into the phi's block — no more, no fewer — because the phi selects the value based on which predecessor edge was taken; an incoming entry for which no edge exists (or a missing entry for a real edge) leaves the selection undefined. The verifier rejects mismatches with `PHI node entries do not match predecessors!`. The real BCIR instance fixed a loop phi that listed `%body` as the back-edge predecessor when the actual back-edge came from `%cont` (the body branched to `%cont` directly or via `%do_prefetch`); the fix was `%i = phi i64 [ 0, %entry ], [ %next, %cont ]`. Whenever you add/remove a `br ... label %X`, you must update every phi in `%X`.
_src: `llvm-training/00-foundations/02-ssa.md`, `llvm-training/08-pitfalls/02-phi-predecessor-mismatch.md`_

**3.** GEP for the `value` field inside an array of structs
Use a single `getelementptr` with two index operands after the base: the first scales by `sizeof(struct)` to pick the array element, the second is a constant `i32` field index. For exercise 006 (`%Entry = type { i32, i64 }`, value = field 1), the verified solution is `%field_ptr = getelementptr inbounds %Entry, ptr %base, i64 %index, i32 1`, followed by `load i64, ptr %field_ptr, align 8`. The leading index is the element step (here `%index`, not a forced 0, because `%base` points at the start of the array); the trailing `i32 1` selects the second struct field. (Verified: assembles cleanly with `llvm-as`.)
_src: `llvm-training/02-types/02-composite-types.md`, `llvm-training/exercises/006-array-of-structs-gep.solution.ll`_

**4.** When pointer `align`/`dereferenceable` should be a parameter attribute
Make them parameter attributes only when the fact holds for *every* dynamic use of the pointer value, not just one access: "Prefer load/store `align` for a known access alignment and parameter `align` only when every use of the pointer value can rely on that alignment." Load/store `align` constrains a single memory access; parameter `align N` asserts the pointer is at least N-byte aligned everywhere and is more specific than only aligning a load/store. `dereferenceable(N)` is a strong promise that permits speculative loads where a fault would otherwise be observable, so it must be true for the lifetime the attribute requires — it is not a comment. For per-call-only facts, attach attributes at the call site instead of the parameter declaration.
_src: `llvm-training/13-advanced-ir/04-attributes.md`_

**8.** Mapping C++/Rust source orderings to LLVM atomic orderings
The mapping is direct: `relaxed` -> `monotonic`, `acquire` -> `acquire`, `release` -> `release`, `acq_rel` -> `acq_rel`, `seq_cst` -> `seq_cst`. For `cmpxchg`, the success ordering applies when the exchange succeeds and the failure ordering applies to the load-only path; the failure ordering cannot be `release` or `acq_rel` and cannot be stronger than success. `acq_rel` is invalid on plain loads/stores; `monotonic` orders only one location (no cross-location ordering). C++ frontends should not invent weaker mappings for `memory_order_consume`, and Rust frontends must remember `UnsafeCell` only grants mutation permission — synchronization comes from the atomic ordering, not the keyword alone.
_src: `llvm-training/11-concurrency/04-memory-model-mapping.md`, `llvm-training/11-concurrency/01-atomic-orderings.md`_

**9.** Fastest way to print IR after `mem2reg` but before `instcombine`
Insert a print pass between the two in a new-pass-manager pipeline: `opt -S -passes='mem2reg,print<module>,instcombine' input.ll -o output.ll`. The new PM exposes `print<module>`, `print<function>`, and analysis printers like `print<loops>`/`print<scalar-evolution>`; pair with `-disable-output` if you only want the diagnostic dump. Always include `-S` for textual IR (otherwise `opt` may emit bitcode). For a tighter before/after view of one pass, `opt -S -passes='print<function>,mem2reg,print<function>' ... -disable-output`.
_src: `llvm-training/07-optimization/05-debugging-passes.md`_

**10.** Loop Vectorizer vs SLP Vectorizer input patterns
The **Loop Vectorizer** acts on countable loops: a recognizable induction variable, a computable or runtime-guardable trip count, unit/simple-stride loads/stores, no unsafe loop-carried dependencies (reductions allowed), and provable/guardable non-aliasing — it widens iterations into `<N x T>` and adds a scalar remainder loop. The **SLP Vectorizer** needs *no loop*; it packs isomorphic straight-line scalar operations within a basic block (e.g. four parallel `load`/`add` chains on adjacent data) into one vector tree using `insertelement`/`extractelement`/`shufflevector`. Key distinction: loop vectorization parallelizes across iterations of a loop; SLP parallelizes independent matching scalar operations in straight-line code.
_src: `llvm-training/09-vectorization/01-loop-vectorizer.md`, `llvm-training/09-vectorization/02-slp-vectorizer.md`_

**11.** When to consult the vector-predication chapter
Consult it when a loop is *almost* vectorizable but needs per-lane masks or target-predicated instructions: dynamic trip counts where scalar remainder loops dominate runtime; targets with native predication (SVE-style scalable `<vscale x N x T>` vectors); lane-local branches that can become masks instead of CFG splits; and BCIR lanes with enable bits / validity masks that map naturally to vector predicates. Core constructs are masks (`<N x i1>`), predicated/masked ops, tail handling, and `select`-based merges (`select <4 x i1> %mask, %new, %old`), plus masked load/store and gather/scatter intrinsics. For BCIR, predication should cross the optimization boundary as explicit masks until the pass that can legally lower them (after semantic BCIR lowering, SCCP poison repair, and loop canonicalization).
_src: `llvm-training/09-vectorization/03-vector-predication.md`_

**12.** Object-layer artifacts to inspect when a JIT reports a missing symbol
Debug from the object layer outward along IR -> instruction selection -> `MachineInstr` -> regalloc -> `MCInst` -> `MCStreamer`/`MCAssembler` -> object bytes/symbols/relocations. Inspect the emitted object's **symbol table** (`llvm-nm` — is the name there, mangled correctly?), its **relocations** (`llvm-objdump -dr`, `llvm-readobj --relocations --symbols` — what symbol/kind/addend does each fixup reference?), and the `MCExpr`/`MCFixup` that became those relocations. Common causes: mangled-vs-unmangled name mismatch, symbol not added to the JIT dylib, a relocation against a helper that was optimized away, or visibility/prefix rules changing the final symbol name.
_src: `llvm-training/12-backend-jit/04-mc-and-relocations.md`_

**13.** ABI attributes that must stay synchronized between declarations and definitions
ABI/call-boundary attributes must match on both sides: `byval(<ty>)`, `sret(<ty>)`, `inreg`, `zeroext`/`signext`, `inalloca(<ty>)`/`preallocated(<ty>)`, plus language hooks `swiftself`/`swifterror` and the calling convention itself (`ccc` vs `fastcc`/`swiftcc`). These describe how source types cross the target ABI (register vs stack placement, hidden struct-return pointers, narrow-int extension) and belong in the target-aware type-lowering layer, not a late cleanup pass. A wrapper that drops `sret`, omits `byval` alignment, adds `inreg` on only one side, or changes the calling convention can corrupt caller stack slots or pass stale pointers; a copied `musttail` over such a mismatch becomes a verifier failure or an ABI-invalid tail jump.
_src: `llvm-training/13-advanced-ir/04-attributes.md`_

**14.** Why an `add nsw` + `icmp` branch is verifier-valid but unsafe; where `freeze` helps
`add nsw` produces **poison** on signed overflow (the `nsw` promise is violated). Poison propagates through the following `icmp`, so for overflowing inputs the branch condition becomes poison, and branching on a poison `i1` is undefined behavior — yet the IR still parses and verifies because the verifier checks structure, not runtime overflow. `freeze` fixes this: `freeze` the poison-capable value (the `add nsw` result, or the `icmp` result) before it feeds the branch, which converts poison/undef into one fixed arbitrary concrete value so the branch direction is at least well-defined. Insert `freeze` before speculative branches/switches/selects and before vector masks whenever the condition derives from poison-capable arithmetic (`nsw`, `udiv exact`, `inbounds`).
_src: `llvm-training/13-advanced-ir/05-poison-undef-freeze.md`_

**15.** Which fast-math flags allow which relaxations
Per-instruction FMFs: `nnan` (ignore NaN operands/results), `ninf` (ignore +/-infinity) — the NaN/infinity assumptions; `nsz` (sign of zero insignificant, `+0.0`/`-0.0` interchangeable) — signed-zero changes; `arcp` (allow reciprocal, rewrite division as multiply-by-reciprocal); `contract` (fuse `fmul`+`fadd` into FMA, one rounding); `afn` (approximate math functions like exp/log/sin/sqrt); `reassoc` (reassociation, e.g. `(a+b)+c` -> `a+(b+c)` or a tree reduction). `fast` is shorthand for the full aggressive set. The safe rule: attach a flag only when source semantics prove it for every dynamic execution; default to strict FP, prefer narrow flags (`contract` alone, `nnan ninf` alone) over `fast`, and avoid FMFs when recovering exact binary behavior or when NaN/inf/rounding/signed-zero is observable.
_src: `llvm-training/13-advanced-ir/06-fast-math-flags.md`_

**16.** Why a crypto function safe in static IR can still leak on a CPU
Static IR can flag suspicious patterns (secret-dependent `br i1`, secret-indexed table lookups/GEPs, early exits revealing bit-length) but cannot model the microarchitecture: data-dependent cache access patterns, branch-predictor state, variable-latency instructions (`sdiv`, `urem`), speculative execution, execution-port contention, prefetchers, TLB behavior, and code-layout effects introduced after instruction selection and linking. So even branch-free, table-free-looking IR can leak via timing/cache once compiled with production optimization/LTO/PGO and run on real hardware. A constant-time review must add dynamic evidence (paired public/secret-class inputs) and counters, not rely on IR shape alone.
_src: `llvm-training/15-binary-analysis/01-microarchitecture-side-channels.md`_

**17.** Build artifacts to preserve to explain a PGO/LTO/BOLT binary
Preserve the evidence of the non-IR decisions: profile data / profile summaries (branch weights, function entry counts, `!prof` metadata), optimization remarks, ThinLTO module summaries and import lists, inline remarks, LTO cache keys, and the final symbol map/table; for BOLT, the post-link profile and the function/block reordering record. These let you reconstruct why hot/cold splitting, cross-module inlining, internalization, or block layout changed. PGO+LTO and BOLT can change binary *shape* without changing source semantics — cross-module inlining specializes and duplicates code, hides function boundaries, and perturbs layout; BOLT reorders functions/blocks and rewrites branches entirely after IR is gone — so only the saved artifacts explain the resulting binary.
_src: `llvm-training/07-optimization/06-pgo-lto-bolt.md`_

**24.** Facts that must stay in executable IR/ABI data, not only diagnostic metadata (ex. 028-031)
Anything execution depends on must be lowered as ordinary SSA operands, memory fields, function arguments, or intrinsic parameters — never carried only in metadata. That means: resource addresses/IDs (lowered to registry GEPs and base-pointer loads), operation effects and ordering constraints (real `@bcir.op.barrier`/atomic ops when ordering is correctness), runtime-call status returns (preserved, not dropped), prefetch `rw`/locality/cache values (emitted as `immarg` constants in the `llvm.prefetch` call), and explicit byte strides. `!bcir.diag`/`!bcir.ham` and provenance annotations are advisory and may be dropped by optimizers, so they must not affect semantics — if execution needs the value, it is an operand, not metadata.

**25.** Distinguishing a custom dialect op, an LLVM dialect op, and final textual `.ll` (ex. 032-034)
A **custom dialect op** lives in a domain namespace (e.g. `bcir.*`, or structured dialects `scf`/`affine`/`linalg`/`vector`/`memref`/`arith`/`func`) and carries high-level semantics not yet expressible in LLVM. An **LLVM dialect op** is MLIR modeling LLVM IR concepts (`llvm.func`, `llvm.add`, `llvm.load`, `llvm.br`) inside MLIR regions/blocks/symbol tables — it is still `.mlir`, with MLIR syntax and verifier. **Final textual `.ll`** is LLVM IR assembly parsed by `llvm-as`, obeying LLVM module/function/basic-block grammar. Crucially LLVM-dialect text is not copy-pasteable into a `.ll` file: translating LLVM dialect to LLVM IR is a final serialization step (via `mlir-translate`), not a rename, and the two have different syntax and verifiers.
_src: `llvm-training/14-mlir-bridge/03-lowering-to-llvm-dialect.md`_

**26.** Which artifacts to inspect first for backend/JIT exercises 035-037
The diagnostic order is: (1) confirm **`JITDylib` symbol definitions** — is the name registered with the right linkage/search order; (2) examine **JITLink edges** (from the object relocation table) to see which symbols the generated object actually references; (3) dump **object symbols** with `llvm-nm` (presence, mangling, weak/strong, local/global binding); (4) dump **relocations** with `llvm-objdump -dr` / `llvm-readobj --relocations --symbols` (kind, section offset, target symbol — the backend's concrete dependency list). **TableGen-generated records** are only relevant for the instruction-encoding (TableGen-to-`MCInst`) exercise and are inspected at the `.td` source level, not edited as generated `.inc`.

**27.** Why binary-analysis chapters are evidence, not LLVM IR examples
Dynamic traces, hardware counters, PGO/LTO/BOLT artifacts, and BCSA CSV features describe what the *final executable* did — reflecting profile data, link-time decisions, object layout, codegen, dynamic inputs, and physical CPU behavior — so they are post-codegen evidence, not assemble-able IR. The tiny CSVs document schema and reasoning flow, not portable benchmark numbers, and each is classified in `evidence-manifest.json` (`deterministic`, `host-sensitive`, or `schematic`); they are excluded from `llvm-as`/`opt -passes=verify`. Static IR features remain a triage signal that can support or weaken a correspondence hypothesis but never prove semantic equivalence.
_src: `llvm-training/15-binary-analysis/README.md`, `llvm-training/EXAMPLES.md`_

## Path-specific self-test

### After Path 1
- **What does SSA stand for and why does it require phi nodes?** Static Single Assignment: every value (`%name`) is defined exactly once. Because a name cannot be reassigned, when control flow merges values from different predecessor paths you cannot overwrite a variable — you need a `phi` at the block start to pick the incoming value according to which predecessor edge was taken (e.g. `%x = phi i32 [ 1, %if_true ], [ 2, %if_false ]`). _src: `llvm-training/00-foundations/02-ssa.md`_
- **Difference between `@foo` and `%foo`?** `@foo` is module-scope (global/constant/function symbol, visible across functions and possibly modules); `%foo` is a function-scoped SSA local defined once. `@` is always module-scope, `%` always function-scope. _src: `llvm-training/01-syntax/01-modules-functions-blocks.md`_
- **Why must a basic block end with a terminator?** A basic block is straight-line code ending in exactly one terminator (`ret`, `br`, `switch`, `indirectbr`, `invoke`, `callbr`, `resume`, `catchswitch`, `catchret`, `cleanupret`, `unreachable`); the terminator defines the CFG edges out of the block. Falling off the end is UB and the verifier rejects a block with no terminator ("Block does not have a terminator instruction") or with more than one. _src: `llvm-training/01-syntax/01-modules-functions-blocks.md`_

### After Path 2
- **Type of the pointer returned by `alloca i32`?** `ptr` — an opaque pointer (address space 0 by default). The element type `i32` is spelled in the `alloca` instruction, not baked into the pointer type. _src: `llvm-training/02-types/02-composite-types.md`, `04-memory/01-alloca.md`_
- **Where do `load`/`store`/`getelementptr` spell the access/element type in opaque-pointer IR?** On the instruction itself: `load i32, ptr %p`, `store i32 %v, ptr %p`, and `getelementptr inbounds %T, ptr %base, ...` — the value/element/source-element type is written explicitly because the `ptr` carries no pointee type. _src: `llvm-training/02-types/02-composite-types.md`, `EXAMPLES.md`_
- **Why is `add i32 (load ...), 1` invalid as a single expression?** LLVM IR is not an expression language; each instruction produces a named SSA result and instructions cannot be nested as operands. You must name the load first (`%v = load i32, ptr %p`) then `%r = add i32 %v, 1`. _src: `llvm-training/08-pitfalls/01-nested-instruction-expressions.md`, `00-foundations/02-ssa.md`_
- **When does `br i1` need two labels, and what's the condition's type?** A *conditional* branch needs both a true and a false label (`br i1 %cond, label %t, label %f`); the condition is type `i1`. An unconditional branch is `br label %dest` with one label and no condition. _src: `llvm-training/05-control-flow/02-conditional-br.md`, `01-syntax/01-modules-functions-blocks.md`_

### After Path 3
- **Follow an instruction `!dbg` back to file/line/column?** The `!dbg` attaches a `DILocation` (`line`, `column`, `scope`); the scope chains through `DILexicalBlock`/`DISubprogram` to a `DIFile` (and `DICompileUnit`) giving the source filename, so you read line/column from the `DILocation` and the path from the `DIFile` it scopes to. _src: `llvm-training/06-metadata/02-debug-info.md`_
- **Why does the grammar separate `Linkage` and `ExternLinkage`?** Definitions (`define`) and declarations (`declare`) accept different linkage sets: a body-less external declaration cannot take definition-only linkages (e.g. `private`/`internal` local-definition forms), so the grammar uses distinct productions (`Linkage` vs `ExternLinkage`) to allow only the legal linkage keywords in each position. _src: `llvm-training/10-grammar/` (`llvm-ir.tm`, `README.md`), `01-syntax/01-modules-functions-blocks.md`_
- **How do `mem2reg`, `instcombine`, and `default<O2>` differ in scope/intent?** `mem2reg` promotes promotable `alloca`/load/store into SSA registers + phis (single targeted transform). `instcombine` is intentionally *local* algebraic/peephole canonicalization (no control-flow reasoning). `default<O2>` is the whole balanced optimization *pipeline* — many ordered analyses and transforms (including the above) chosen by the pipeline builder. _src: `llvm-training/07-optimization/04-optimization-levels.md`, `05-debugging-passes.md`_
- **Why might `-O3` be a bad default for a size-sensitive workload?** `-O3` is more aggressive for performance and includes size-expanding transforms (extra inlining/unrolling), increasing code size and compile time without guaranteed speedup; `-Os`/`-Oz` explicitly avoid the size-expanding passes, so they are the right defaults when size matters. _src: `llvm-training/07-optimization/04-optimization-levels.md`_
- **`dso_local` vs `dso_preemptable`?** `dso_local` asserts the symbol resolves to a definition within the current linkage unit (no runtime interposition), enabling direct/relative references; `dso_preemptable` means another module could interpose/override it at load time, forcing indirection (e.g. via the GOT/PLT). _src: `llvm-training/04-memory/03-global-variables.md`, `01-syntax/01-modules-functions-blocks.md`_
- **Layout convention for `%bcir.claim`-style aggregates; what breaks on field-count disagreement?** Such named aggregates have one canonical structural body (field order/types fixed) and must be defined from a single source of truth shared by all consumers. If two modules disagree on the field count/types, `llvm-link` either errors ("type definitions differ") or silently produces two types (`%S` and `%S.0`); downstream `getelementptr` then computes wrong field offsets, corrupting reads/writes. The fix is a canonical schema module reused everywhere. _src: `llvm-training/08-pitfalls/05-type-schema-drift.md`_

### After Path 4
- **Loop Vectorizer rather than SLP?** Expect the Loop Vectorizer on a countable loop with an induction variable and consecutive/strided memory across iterations; expect SLP on straight-line code with independent isomorphic scalar operations (no loop). _src: `llvm-training/09-vectorization/01-loop-vectorizer.md`, `02-slp-vectorizer.md`_
- **What facts prove predictable access / no unsafe deps?** A simple counted loop with a clear induction variable and exit test; unit-stride array access (`c[i]=a[i]+b[i]`); iterations independent or a recognized reduction pattern; a known or runtime-guardable trip count; and explicit non-aliasing facts — source `restrict`, IR `noalias`/`dereferenceable`, TBAA, and alias-scope metadata. _src: `llvm-training/09-vectorization/04-vectorization-legality.md`_
- **Commands showing successful vs missed remarks?** From source: `clang -O3 -Rpass=loop-vectorize -Rpass-missed=loop-vectorize input.c -c -o /tmp/input.o`; on IR via `opt`: `-pass-remarks=loop-vectorize -pass-remarks-missed=loop-vectorize` with `-passes=loop-vectorize`. _src: `llvm-training/09-vectorization/06-recognizing-vector-ir.md`, `07-optimization/05-debugging-passes.md`_
- **IR clues vectorization occurred?** `<N x T>` vector types, wide vector loads/stores (`load <4 x i32>, ptr ...`), `shufflevector` (common in SLP), and reduction intrinsics like `@llvm.vector.reduce.add.v4i32`; loop vectorization also adds a scalar remainder loop and runtime alias/trip-count checks. Vector IR does not guarantee vector machine code. _src: `llvm-training/09-vectorization/06-recognizing-vector-ir.md`_
- **Why can PGO+LTO or BOLT change binary shape without changing semantics?** Profile-guided cross-module inlining/internalization specializes, duplicates, and reorders code and perturbs block layout; BOLT reorders functions/blocks and rewrites branches post-link after IR is gone. These change code shape/layout for performance while preserving observable behavior. _src: `llvm-training/07-optimization/06-pgo-lto-bolt.md`_

### After the backend / JIT path
- **Where do SelectionDAG and GlobalISel fit relative to `MachineInstr`?** Both are *instruction selectors* that run before `MachineInstr`: they consume LLVM IR and produce `MachineInstr` (in virtual registers, still SSA). SelectionDAG builds/legalizes/combines/selects a DAG; GlobalISel goes generic-MIR -> legalize -> regbankselect -> select. After selection comes machine-SSA optimization, then register allocation. _src: `llvm-training/12-backend-jit/01-codegen-pipeline.md`_
- **Why does register allocation happen after machine-code SSA optimizations?** Those machine-SSA passes (machine CSE, copy propagation, peephole/branch folding) rely on virtual-register SSA properties; register allocation destroys SSA by mapping virtuals to physical registers and inserting spills/reloads, so it must run after the SSA-dependent optimizations (and before prolog/epilog insertion, which needs the allocation result). _src: `llvm-training/12-backend-jit/01-codegen-pipeline.md`_
- **Which backend facts come from TableGen `.td`?** Register definitions/classes and `TargetRegisterInfo` tables, instruction operands/assembly/encodings/flags for `TargetInstrInfo`, DAG instruction-selection patterns, calling-convention fragments, and scheduling/itinerary models — emitted by `llvm-tblgen` into `*Gen*.inc`. _src: `llvm-training/12-backend-jit/02-tablegen.md`_
- **Ownership objects to identify before adding modules to an ORC `LLJIT`?** `ExecutionSession` (session state/string pool, must outlive code), `JITDylib` (symbol namespace), `ThreadSafeContext`/`ThreadSafeModule` (own the `LLVMContext`/`Module` you transfer in), and `ResourceTracker` (group definitions for removal). Set the module's data layout from the JIT (`setDataLayout(JIT->getDataLayout())`) before wrapping in `ThreadSafeModule` and `addIRModule`. _src: `llvm-training/12-backend-jit/03-orc-jit.md`_

### After the binary-analysis path
- **Why is a secret-dependent branch in IR not the only side-channel signal?** Because leaks also arise from secret-dependent memory addresses (cache/TLB), variable-latency instructions, speculation, port contention, prefetchers, and post-codegen layout — none visible as a branch in IR. You must also review table lookups/GEP indices on secrets and add dynamic evidence. _src: `llvm-training/15-binary-analysis/01-microarchitecture-side-channels.md`_
- **Which hardware counters to pair with branch/path traces for constant-time review?** Branch misses (paired with path/branch traces for secret-dependent control flow) and cache/memory-hierarchy counters — `cache_misses`, `l1d_misses`, `llc_misses` — plus cycles and instructions retired, compared across paired public/secret-class inputs. _src: `llvm-training/15-binary-analysis/02-dynamic-traces-and-counters.md`_
- **Which PGO/LTO/BOLT artifacts to save before comparing optimized binaries?** Profile data/summaries (branch weights, entry counts), optimization/inline remarks, ThinLTO module summaries and import lists, cache keys, final symbol maps, and BOLT profile + reordering records. _src: `llvm-training/07-optimization/06-pgo-lto-bolt.md`, `15-binary-analysis/04-reproducible-evidence-pipelines.md`_
- **Which interpretable BCSA features are cheap enough for first-pass triage?** Basic-block count, edge count / cyclomatic complexity, normalized opcode histogram, callsite summary, and memory-access summary — compared first, before escalating to graph matching or dense embeddings. _src: `llvm-training/15-binary-analysis/03-interpretable-bcsa-features.md`_

### After the BCIR lowering path
- **Which BCIR claims must be normalized before operation dispatch?** Normalize symbolic resources, lane masks, operation names, and immediate values into canonical claim records first; the pipeline is NORMALIZE -> PACK (fixed-width fields) -> BIND (resource IDs to registry GEPs/base loads) -> DISPATCH (plain IR or runtime wrapper) -> STABILIZE (`freeze` poison-capable predicates) -> ATTACH (metadata only after dataflow is explicit). Claims must stay distinct throughout. _src: `llvm-training/bcir-mapping/06-claim-lowering-pipeline.md`_
- **Which lowering choices produce plain IR, runtime ABI structs, or wrapper calls?** Stable graph fragments and resource lookups become plain LLVM IR (named struct arrays + GEPs + loads); claim/resource records become runtime ABI structs accessed via registry loads; target-specific or opaque-state operations that cannot be expressed as scalar/vector IR become runtime-call wrappers with declared signatures and preserved status returns. _src: `llvm-training/bcir-mapping/09-runtime-call-boundaries.md`, `07-gaadmsf-operations.md`_
- **Which checked examples prove graph/register/HAM/mixed-stride/runtime/diagnostic mappings?** `graph-fragment-struct-gep.ll`, `register-binding.ll`, `ham-hint-prefetch.ll`, `mixed-stride-byte-offset.ll`, `bcir-op-runtime-wrapper.ll`, and `diagnostic-metadata-preservation.ll` respectively (claim lookup adds `claim-resource-lookup.ll`). _src: `llvm-training/bcir-mapping/examples/`_

### After the MLIR integration path
- **Which BCIR concepts belong in a custom dialect rather than directly in `.ll`?** Vertex/edge/attribute graph structure (`!bcir.vertex`/`!bcir.edge`/`bcir.attribute`), HAM hints as explicit `bcir.ham_hint` ops (not silent metadata), register binding as `bcir.bind_register` (required vs optional, lowering to intrinsics/inline-asm for required ones), and mixed-stride graphs (rank/layout as type params/attributes, static strides as dense attributes, dynamic strides as SSA operands) — concepts too high-level or domain-specific to express directly in `.ll`. _src: `llvm-training/14-mlir-bridge/04-bcir-as-custom-dialect.md`_
- **How does LLVM dialect differ from final textual LLVM IR?** LLVM dialect is MLIR (`llvm.*` ops in MLIR regions/blocks, MLIR syntax/verifier, `.mlir` files); final textual IR is `.ll` assembly under LLVM grammar parsed by `llvm-as`. Converting dialect -> IR is a `mlir-translate` serialization step, not a textual rename. _src: `llvm-training/14-mlir-bridge/03-lowering-to-llvm-dialect.md`_
- **Which MLIR examples are review artifacts instead of `llvm-as` inputs?** All `.mlir` files (custom-dialect sketches, LLVM-dialect shapes, lowering-boundary illustrations) are review artifacts checked with `verify-mlir-examples.sh` only when MLIR tools are present; they are never fed to `llvm-as`/`opt -passes=verify`. Only the `.ll` files (e.g. `arith-to-llvm-lowered.ll`, `bcir-vertex-graph-lowered.ll`) are `llvm-as` inputs. _src: `llvm-training/14-mlir-bridge/01-what-is-mlir.md`, `EXAMPLES.md`_

### After the backend/JIT diagnostics path
- **Which missing-symbol evidence comes from ORC ownership vs object symbols/relocations?** Ownership evidence: `JITDylib` definitions and search order, generators, and whether host-process symbols were registered, plus `ExecutionSession`/`ResourceTracker`/`ThreadSafeModule` lifetime. Object evidence: the emitted symbol table (`llvm-nm`) and relocation records (`llvm-objdump -dr`, `llvm-readobj --relocations --symbols`) showing the name/kind/target each fixup needs. _src: `llvm-training/12-backend-jit/03-orc-jit.md`, `05-orc-layers.md`, `04-mc-and-relocations.md`_
- **Why edit TableGen source instead of generated includes?** The `*Gen*.inc` files are produced by `llvm-tblgen` from `.td` sources into the build tree and are overwritten on every build; edits there are lost and the generated files may not even appear in a source-only index. Edit the `.td` source so the change regenerates correctly. _src: `llvm-training/12-backend-jit/02-tablegen.md`, `08-pitfalls/15-tablegen-generated-file-confusion.md`_

### After the repair exercises path
- **Why are invalid fixtures excluded from known-good manifests?** They are intentionally rejected by `llvm-as`/`opt -passes=verify`; including them would break the known-good verification loop and let version-specific failures masquerade as good IR. The `.invalid.ll.txt` naming and the `*invalid*` skip rule keep them out. _src: `llvm-training/EXAMPLES.md`, `exercises/README.md`_

(Top-level known-good examples use `tools/verify-examples.sh`.) _src: `llvm-training/tools/README.md`, `exercises/README.md`_

### After the BCIR mapping path
- **Which claim-lowering stages happen before operation dispatch?** NORMALIZE (canonicalize resources/masks/op-names/immediates), PACK (fixed-width claim fields), and BIND (resource IDs -> registry GEPs and base-pointer loads) all precede DISPATCH; STABILIZE (`freeze`) and ATTACH (metadata) follow. _src: `llvm-training/bcir-mapping/06-claim-lowering-pipeline.md`_
- **When should a BCIR operation become plain LLVM IR versus a runtime-call wrapper?** Express it as plain IR when it maps to scalar/vector LLVM operations or struct/GEP/load-store memory access (stable graph fragments, address arithmetic, prefetch). Use a runtime-call wrapper when it is runtime-owned/target-specific/opaque-state or bulk work not expressible in IR — declared once with exact signatures, small named wrappers, inputs loaded before the call, and status returns preserved. _src: `llvm-training/bcir-mapping/09-runtime-call-boundaries.md`_
- **Why do HAM prefetch operands need immediate constants?** `llvm.prefetch`'s `rw`, locality, and cache-type operands are `immarg` — they select the target-specific prefetch encoding at codegen time and so must be literal constants, not runtime-decoded hint values passed through registers/memory. (Verified: `ham-hint-prefetch.ll` passes `opt -passes=verify` with literal `i32 0, i32 3, i32 1`.) _src: `llvm-training/bcir-mapping/04-ham-hints.md`, `10-metadata-and-diagnostics.md`_
- **Why should diagnostic metadata never carry execution-required semantics?** `!bcir.diag`/`!bcir.ham` and provenance metadata are advisory and may be dropped or not preserved by optimizers; if execution depended on them, dropping them would silently change behavior. So any value execution needs must live in operands, memory fields, arguments, or intrinsic parameters — metadata is only for diagnostics/hints/source correlation passes can safely ignore. _src: `llvm-training/bcir-mapping/10-metadata-and-diagnostics.md`_
