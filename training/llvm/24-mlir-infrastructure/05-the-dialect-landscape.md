# The dialect landscape, and what this corpus does about it

[`README.md`](README.md) says this chapter is not a dialect tour. That refusal is right,
and it creates a problem worth naming: from inside a green CI run, "we teach the framework
rather than the dialect list" and "nobody has noticed that `linalg` has 99 operations and
we name one of them" look exactly alike. Both are silence.

So the landscape is measured, and every dialect answers for itself.

## How big it actually is

MLIR's operation set is two orders of magnitude larger than LLVM's. LangRef defines 67
instructions; the MLIR this corpus is verified against ships roughly two and a half
thousand operations across several dozen dialects. That is not a corpus you read — it is
a corpus you learn to navigate, which is what chapters 01 to 04 are for.

## The four answers a dialect can give

A raw coverage percentage is the wrong number to optimise, and the vector-predication
family shows why. [`../09-vectorization/03-vector-predication.md`](../09-vectorization/03-vector-predication.md)
teaches LLVM's `llvm.vp.*` family — 95 intrinsics — by explaining the two-level mask and
`%evl` model and naming two of them. Ninety-three go unnamed, and that is *good* teaching,
not a gap. A gate that rewarded naming all 95 would push the corpus toward being a worse
copy of the reference manual.

What separates a decision from an oversight is not the count. It is whether anyone wrote
down which one it was. Every dialect therefore carries one of four dispositions in
[`../reference/mlir-dialect-dispositions.json`](../reference/mlir-dialect-dispositions.json):

| Disposition | Means | Must carry |
| --- | --- | --- |
| **taught** | a chapter teaches it | `where` — and that chapter must name a real operation of the dialect, in code |
| **referenced** | named in passing, not taught | the same citation |
| **planned** | in scope, not written yet | `slice` — the work that closes it |
| **declared** | out of scope | `reason`, in words |

`planned` is the one that had to be invented. The other three could not express the honest
state of this corpus: calling `tosa` "out of scope" would be false, because it is squarely
in scope and simply unwritten, and calling it "taught" would be a lie. A gap the corpus has
decided to close is a third thing and needs to be visible as one — with the slice attached,
so an intention cannot quietly become permanent.

## What counts as teaching a dialect

The citation rule is stricter than it looks, and every weaker version of it admitted
something false. This is worth stating because the same trap waits for anyone measuring
coverage of anything:

- A **prose** search credits the `shape` dialect for the sentence "expected vector IR
  shape." Six of these dialect names — `shape`, `index`, `math`, `complex`, `vector`,
  `func` — are ordinary English words.
- Searching **code spans** for `<dialect>.<word>` is better and still wrong. It credits
  `shape.ll`, which is a filename. Worse, it credits the `x86` and `vector` dialects for
  `llvm.x86.pclmulqdq` and `llvm.vector.reduce.or.v4i1` — LLVM *intrinsics* that happen to
  contain a dialect's name.
- Even extracting inline code spans is a trap if you do it with a regex that cannot tell an
  opening backtick from a closing one: in ``a constant `i32` field index.`` such a pattern
  starts at the backtick that *closes* `i32` and matches " field index.".

So the rule is exact rather than clever: a chapter is credited with a dialect only when it
names **an operation from that dialect's own snapshot list**, in a code block or an inline
code span. There is no heuristic left to fool.

## Two disagreements the measurement found

Both are recorded rather than smoothed over, because in a green run an unexplained
disagreement and a broken extraction look identical:

- **`vcix` ships operations no registry lists.** The generated headers define two `vcix`
  operations; `mlir-opt --show-dialects` does not mention the dialect. It is a RISC-V
  vendor co-processor dialect outside the default registration set. Headers and registry
  disagreeing is normal for a vendor dialect — but a gate that did not know that would
  report it as an extraction failure.
- **`dlti` registers with zero operations.** That is correct: DLTI models data layout and
  target information as attributes and types only. It is also this gate's anti-vacuity
  canary. An extraction bug that silently returned nothing would look exactly like DLTI, so
  DLTI is the one dialect allowed to look like that, and it is allowed by name.

## Pitfalls checklist

- Do not read a low operation-coverage number as a defect on its own. Ask what the
  disposition says; the number without the disposition is not a finding.
- Do not mark a dialect taught because a chapter mentions its name. Mention is not
  teaching, and half these names are ordinary words.
- Do not add a dialect to `planned` without a slice. That is how a gap stays open for a
  year while looking handled.
- Do not assume the dialect list is a property of the MLIR *release*. It is a property of
  the *build* — see [`README.md`](README.md), where two builds of LLVM 23 disagree.

## Checks

[`../tools/verify-mlir-coverage.py`](../tools/verify-mlir-coverage.py) reads the operation
set out of the installed MLIR two independent ways — `mlir-tblgen --gen-op-doc` and the
`getOperationName()` accessor in the generated headers — and requires the second to contain
the first, so an extraction that quietly under-reported would fail rather than flatter the
coverage figure. It then requires a disposition for every dialect in the snapshot, a
citation that names a real operation for every `taught` and `referenced` one, a slice for
every `planned` one, a reason for every `declared` one, and an entry in the misalignment
table for each of the two disagreements above. The table in this chapter is generated, not
typed.
